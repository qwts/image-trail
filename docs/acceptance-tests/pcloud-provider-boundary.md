# pCloud Provider Boundary

Issues: #199, #203, #223

## Scope

- Settings shows the Cloud backup pCloud provider in the live Import / Export utility stack.
- Connect pCloud requests optional access only to `https://*.pcloud.com/*` before OAuth; denial does not open OAuth or store a token.
- Connect pCloud uses the browser extension OAuth token flow through `chrome.identity.launchWebAuthFlow`.
- The pCloud OAuth access token is stored only in background-owned extension storage and is not returned to the content script or panel UI.
- Only `api.pcloud.com` and `eapi.pcloud.com` are accepted as API hosts.
- Back up now creates a versioned, password-encrypted manifest plus independently encrypted metadata, bounded bookmark-record, and one-original parts. Legacy encrypted single-file backups remain restorable.
- The backup password is entered for that upload only and is not stored.
- One PBKDF2-derived key is reused only within that backup; every manifest/part encryption uses a fresh AES-GCM IV, and each part authenticates its backup id, part id, and kind as additional data.
- Bookmark records target 512 KiB parts, while encrypted originals are requested, messaged, uploaded, downloaded, and imported one at a time. A single record or original can be larger than that target, but cumulative original bytes are never assembled into one extension message.
- The background provider creates or reuses `/Image Trail/backups`, uploads with `nopartial=1` and `renameifexists=1`, waits for each file to appear in `listfolder`, and verifies each encrypted object before reporting success. The primary path downloads and byte-compares the remote file; the fallback compares pCloud SHA-1 with Image Trail's SHA-1 of the exported bytes.
- The encrypted manifest records the backup id, schema version, created time, counts, exact part filenames and file ids, sizes, SHA-256 hashes, and contiguous restore order. It is uploaded only after every referenced part verifies.
- Part filenames end in `.image-trail-part.json`; only the final manifest ends in `.image-trail-encrypted.json`. Incomplete attempts therefore do not appear in the restore chooser.
- Image Trail computes SHA-256 over every encrypted object. Backup history is written only for the final manifest, is newest-first, and is limited to 20 sanitized metadata records.
- Backup history remains visible after panel/page reload and pCloud disconnect.
- Back up and restore expose progress and cooperative cancellation between provider requests. A canceled/failed pre-manifest backup attempts to delete every verified part; cleanup accepts only exact file ids whose current files are part artifacts under `/Image Trail/backups`, reports any remaining ids, and can be retried safely.
- Choose restore file lists manifests only. Chunked preview decrypts the manifest, checks unique ids, exact generated filenames, contiguous ordering, counts, size, SHA-256, and authenticated part identity, then downloads only metadata/record parts before showing a no-write preview.
- Confirmation revalidates metadata and downloads/imports encrypted originals one at a time. Part downloads first prove that the exact file id and manifest filename belong to `/Image Trail/backups`.

## Manual Check

1. Load the unpacked extension, copy its ID from `chrome://extensions`, and register
   `<extension-id>.chromiumapp.org` as an allowed redirect host for the Image Trail
   pCloud app. The OAuth callback generated by Image Trail is
   `https://<extension-id>.chromiumapp.org/pcloud`.
2. Open Image Trail Settings.
3. Expand Cloud backup and confirm pCloud starts disconnected.
4. Click Connect pCloud and confirm Chromium requests access only to pCloud hosts.
5. Deny once and confirm OAuth does not open, the provider stays disconnected, and the error explains how to retry.
6. Click Connect pCloud again, approve the pCloud request, and complete authorization.
7. Confirm the provider returns to connected state with the API host visible.
8. Capture or pin enough durable queue records to create more than one record part, including at least two stored originals.
9. Enter a cloud backup password of at least 4 characters.
10. Click Back up now.
    Expected: the button enters a backing-up state, reports per-part progress, and finishes only after publishing the verified manifest.
11. Confirm Backup history shows pCloud, `/Image Trail/backups`, filename, completion time, size, Image Trail SHA-256, and whether downloaded bytes or pCloud checksum verified the export.
12. Confirm pCloud contains metadata/record/original files ending in `.image-trail-part.json` plus one final manifest ending in `.image-trail-encrypted.json` under `/Image Trail/backups`.
13. Confirm only the manifest appears in Backup history and Choose restore file.
14. Start another backup and cancel it while parts are uploading.
    Expected: the current provider request finishes, uploaded parts are removed, no manifest is published, and any cleanup failure names only the remaining pCloud file ids.
15. Reload the page, reopen Image Trail Settings and pCloud, and confirm the completed backup-history record remains visible.
16. Click Choose restore file, select the completed manifest, enter its password, and confirm restore preview appears before any bookmark, album, key, or original import.
17. Delete or rename one referenced part in pCloud and retry preview.
    Expected: restore fails closed on folder membership, filename, size, SHA-256, identity, or decryption validation.
18. Restore the part, preview again, confirm import, and watch originals restore one at a time.
19. Cancel a fresh restore between original parts, retry it, and confirm the idempotent import completes without duplicate durable bookmarks.
20. Restore a legacy encrypted single-file pCloud backup and confirm the existing preview/import path still works.
21. Cancel the preview, then click Disconnect.
    Expected: the provider returns to disconnected state and backup history remains visible.
22. Inspect `chrome.storage.local` from the extension service worker.
    Expected: `imageTrail.backupHistory` contains at most 20 sanitized metadata records; it contains no access token, password, or encrypted backup contents. The connection token record is removed after disconnect.

The redirect registration must be updated whenever the installed extension ID changes.
Unpacked builds without a manifest key derive their ID from the extension path, so a
different worktree can require a different pCloud redirect host.
